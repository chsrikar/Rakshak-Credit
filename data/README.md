# Rakshak Credit — Phase 1 Data Pack

## What is included
- `applicants.csv`: shared application form, location, purpose, requested loan and self-reported baseline fields.
- `gig_worker_profiles.csv`: gig-specific earnings, workdays, occupation tenure, work costs, household costs and evidence type.
- `shopkeeper_profiles.csv`: shop type, business age, customer count, average bill, sales, inventory, operating costs, rent, supplier dues and evidence type.
- `transactions.csv.gz`: six months of synthetic transaction activity.
- `engineered_features_with_audit.csv`: engineered cash-flow and contextual numeric features plus synthetic outcome/audit fields.
- `model_ready_dataset.csv`: selected numeric features, synthetic target and applicant-level split.
- `train.csv`, `validation.csv`, `test.csv`: ready-to-load partitions.
- `DATA_DICTIONARY.json`, `model_feature_list.json`, `data_report.json`.

## Run
```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
# Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
python src/generate_data.py --applicants 1500 --seed 42 --out data
```

The generated data is reproducible with the same seed. It is synthetic and intended for a hackathon prototype only.

## Important model rules
1. The target `synthetic_missed_payment` is generated by a toy formula. It is NOT an observed repayment label. Model metrics only demonstrate the pipeline, not real lending accuracy.
2. Never use `synthetic_target_probability_for_documentation_only` as a model input.
3. `applicant_id` and `split` are metadata; drop them before training.
4. Location, free-text loan purpose, platform/employer names and business type are retained for product context but excluded from the starter feature list. Consider proxy bias and data minimization before adding context to a real model.
5. Keep affordability/loan-limit policy separate from ML predictions.
6. SHAP explains how a model used input features; it does not establish causal reasons.
7. The demo consent field is synthetic. Real Account Aggregator integration and actual credit decisions require authorized integrations, explicit consent, data protection and applicable regulatory/compliance review.

## Proposed flow
Borrower form -> consent/demo data import -> data validation -> feature engineering -> LightGBM baseline -> SHAP reasons -> separate affordability policy -> borrower result + lender dashboard + fairness metrics.
